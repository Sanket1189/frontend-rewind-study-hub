1. What semantic HTML means

Semantic HTML uses elements according to the meaning of their content. A <nav> means "this region contains important navigation." A <main> identifies the page's primary content. A <button> means "this control performs an action."

A <div> has no built-in meaning. It is useful when you only need a styling or layout wrapper, but it should not replace an element that already communicates the correct purpose.

Semantic elements help four groups at once:

  1. Browsers receive built-in behavior, such as keyboard activation for buttons.
  2. Assistive technology receives roles, names, states, and page landmarks.
  3. Search engines understand the content structure more clearly.
  4. Developers can read and maintain the markup more easily.

2. Important structural elements

<header>

Introductory content for a page or section. It often contains branding, a heading, or navigation. A page may contain more than one header.

<nav>

A region containing major navigation links. Not every small collection of links needs to be a navigation landmark.

<main>

The unique primary content of the page. Normally, a document should have one visible main region.

<section>

A thematic section of content, normally with its own heading. If you cannot give the section a meaningful heading, a <div> may be more appropriate.

<article>

Self-contained content that could make sense independently, such as a job posting, news article, product card, or forum post.

<aside>

Content related to the surrounding content but not part of its main flow, such as related jobs or supporting information.

<footer>

Footer information for a page or section, commonly copyright, authorship, policies, or secondary links.

3. Headings describe the content outline

Headings are not selected because of their default font size. They describe hierarchy:

  • <h1> is the page's main subject.
  • <h2> introduces a major subsection.
  • <h3> introduces a subsection inside an <h2> section.

CSS controls visual size. HTML controls meaning. Avoid jumping from <h1> to <h4> merely because <h4> looks smaller.

4. Link versus button

Use a link when the result is navigation: opening another page, moving to a section, or downloading a resource.

Use a button when the result is an action: submitting a form, opening a dialog, changing a filter, saving, or deleting.

Native controls already include keyboard and accessibility behavior. A button can be focused with the keyboard and activated with Enter or Space. Adding role="button" to a <div> only changes how assistive technology may announce it; it does not automatically add correct keyboard behavior, focus behavior, form behavior, or button styling.

5. Accessible forms

Every input needs a label

The label tells the user and assistive technology what data belongs in a field.

<label for="candidate-name">Full name</label> <input id="candidate-name" name="candidateName" type="text" />

The label's for value matches the input's id. Clicking the label also focuses the field. Placeholder text is optional guidance, not a label: it disappears while typing and may have poor contrast.

Group related controls

Use <fieldset> and <legend> when multiple controls share one question, such as experience level or notification preferences.

<fieldset> <legend>Experience level</legend> <label><input type="radio" name="level" value="junior" /> Junior</label> <label><input type="radio" name="level" value="mid" /> Mid-level</label> </fieldset>

Instructions and errors must be connected

aria-describedby connects an input to extra text such as a hint or error. aria-invalid="true" tells assistive technology that the current value is invalid.

<label for="email">Email</label> <input id="email" name="email" type="email" aria-describedby="email-hint email-error" aria-invalid="true" /> <p id="email-hint">Use the address recruiters should contact.</p> <p id="email-error">Enter a valid email address.</p>

In a real application, only add aria-invalid="true" and show the error after validation fails. Error meaning should not depend on red color alone; include understandable text.

Client validation is not security

Attributes such as required, minlength, and type="email" improve user experience, but the server must still validate all submitted data. Browser validation can be bypassed.

6. Keyboard and focus basics

Interactive controls should be reachable in a logical DOM order. Tab moves forward; Shift+Tab moves backward. Avoid positive tabindex values such as tabindex="4", because they create a second manual focus order that becomes difficult to maintain.

Keep the visible focus outline. You may restyle it with :focus-visible, but do not remove it without a clear replacement.

Use tabindex="0" carefully to add an element to the normal tab order, and tabindex="-1" when code needs to move focus to an element that should not be part of normal Tab navigation.

7. ARIA: use it only to fill semantic gaps

Prefer native HTML when it provides the needed element and behavior. ARIA is useful for complex widgets or dynamic states that HTML alone cannot express, but incorrect ARIA can make an interface more confusing.

Think of an ARIA role as a promise. If you declare that a custom component is a button, tab, menu, or dialog, you must also implement all expected keyboard behavior, focus handling, states, and naming.

Good use:

<button type="button" aria-pressed="false">Mute</button>

Unnecessary and incomplete use:

<div role="button">Submit application</div>

The correct version is simply:

<button type="submit">Submit application</button>

Common mistakes and their fixes

Mistake Why it is a problem Better choice
Clickable <div> used as an action No native button behavior Use <button>
Button used to navigate to another page Meaning and browser behavior are wrong Use <a href="...">
Placeholder used as the only label It disappears and may not provide a reliable name Add a visible <label>
Heading chosen by visual size Breaks the document hierarchy Choose by level; style with CSS
Positive tabindex values Creates a fragile manual focus order Keep logical DOM order
outline: none without replacement Keyboard users cannot locate focus Use a visible :focus-visible style
ARIA added to a native element unnecessarily Can override correct semantics Prefer the native element
Client-side validation treated as security Browser checks can be bypassed Validate again on the server

Interview question and model answer

Question: Why are semantic HTML and accessibility important in a React application?

Model answer:

Semantic HTML gives the interface correct structure and built-in behavior before React adds state or interactivity. I use native elements such as buttons, links, labels, fieldsets, and landmarks because they provide reliable keyboard behavior and useful information to assistive technologies with less custom code. This improves accessibility, maintainability, SEO, and automated testing. I use ARIA only when native HTML cannot express a component's required role or state, because ARIA changes semantics but does not automatically implement keyboard or focus behavior. For dynamic React components such as dialogs, I also manage focus, expose validation messages, and test the complete flow with a keyboard.
