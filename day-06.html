Practical Accessibility, Focus, and Form Errors

Practice keyboard navigation, visible focus, accessible form errors, modal focus management, and realistic testing.

1. Accessibility is behavior, not decoration

Semantic HTML gives assistive technology meaning, but interactive accessibility also depends on behavior. A control must be reachable, understandable, operable, and predictable. Its state changes and errors must be perceivable without relying only on color, motion, sight, or a mouse.

Use native elements first. A real button, input, select, and dialog include browser behavior that a styled div does not. ARIA can communicate semantics and state, but it does not add click handling, keyboard support, focus movement, or validation logic.

2. Think like a keyboard user

Test the page without touching the mouse:

  • Tab moves forward through interactive elements.
  • Shift + Tab moves backward.
  • Enter follows links and normally activates buttons.
  • Space activates buttons and toggles native checkboxes.
  • Arrow keys operate many native grouped controls such as radio buttons and selects.
  • Escape commonly closes a modal dialog.

The focus order should follow the DOM and the visual reading order. Avoid positive tabindex values because they create a second, fragile navigation order. Use tabindex="-1" only when an otherwise non-focusable element must receive focus programmatically; it does not add the element to normal tab navigation.

3. Visible focus is required feedback

Keyboard users need to know which control will receive the next action. Do not remove the browser outline unless you replace it with an equally visible indicator.

:where(a, button, input, select, textarea):focus-visible { outline: 3px solid #f59e0b; outline-offset: 3px; }

:focus-visible generally shows the strong indicator when the browser decides focus needs to be visible, especially during keyboard navigation. Test the indicator against every background and on every control state.

4. Labels, names, and descriptions

Every form control needs an accessible name. A visible <label> explicitly connected with for and id is the most reliable choice.

<label for="email">Email address</label> <input id="email" name="email" type="email" aria-describedby="email-hint" /> <p id="email-hint">Use the address where recruiters can reach you.</p>

The label tells the user what the field is. aria-describedby adds supporting information. A placeholder is neither: it disappears during typing, can have weak contrast, and is not a dependable replacement for a persistent label.

Group related options with fieldset and legend. Give icon-only buttons an accessible name with visible text or aria-label. Prefer visible text when space permits because it helps everyone.

5. Required fields and instructions

Mark required fields in the HTML and explain the notation before the form. Do not rely on an asterisk alone.

<p id="required-note">Fields marked required must be completed.</p> <label for="role">Preferred role <span aria-hidden="true">*</span></label> <select id="role" name="role" required aria-describedby="required-note"> <option value="">Choose a role</option> <option>Frontend developer</option> </select>

Native constraints provide useful semantics and a fallback. Product validation may add clearer messages, but it should not erase native meaning.

6. An accessible validation sequence

When submission fails, the interface should do more than add a red border:

  1. Prevent submission.
  2. Show a concise error summary near the form heading.
  3. Provide links from the summary to invalid fields.
  4. Put a specific correction beside each invalid field.
  5. Connect the message using aria-describedby.
  6. Set aria-invalid="true" while the value is invalid.
  7. Move focus to the summary or first invalid field.
  8. Preserve every value the user already entered.
<div id="error-summary" role="alert" tabindex="-1" hidden> <h2>Please fix the following</h2> <ul><li><a href="#email">Enter a valid email address.</a></li></ul> </div> <input id="email" aria-invalid="true" aria-describedby="email-hint email-error" /> <p id="email-error">Enter an address such as name@example.com.</p>

Color may reinforce the error, but the text and programmatic connection carry the meaning.

7. Dynamic announcements

Content inserted after an action may need a live region so a screen reader announces it without moving focus.

<p id="save-status" role="status" aria-live="polite"></p>

Use role="status" or a polite live region for non-urgent confirmation. Use role="alert" sparingly for an important error that needs immediate attention. Do not announce every keystroke or duplicate information already conveyed by focus.

8. Focus management for modal dialogs

A modal temporarily makes the page behind it unavailable. Its focus lifecycle is part of the component:

  1. A real button opens the modal.
  2. Focus moves to a useful element inside it.
  3. Tab and Shift + Tab remain inside while it is modal.
  4. Escape and an explicit button can close it.
  5. Focus returns to the button that opened it.

The native <dialog> element plus showModal() supplies modal semantics, background inertness, focus containment, and Escape behavior in modern browsers. It usually needs less custom code than rebuilding a modal with generic elements and ARIA.

<button type="button" id="open-dialog">Review submission</button> <dialog id="review-dialog" aria-labelledby="review-title"> <h2 id="review-title">Review submission</h2> <p>Confirm that the details are correct.</p> <form method="dialog"> <button value="cancel">Go back</button> <button value="confirm" autofocus>Confirm</button> </form> </dialog>
const opener = document.querySelector("#open-dialog"); const dialog = document.querySelector("#review-dialog"); opener.addEventListener("click", () => dialog.showModal());

autofocus declares the intended initial target. A button inside a method="dialog" form closes the dialog. The browser returns focus to the invoking control when it is still available.

9. Choose initial focus deliberately

For a short confirmation, focus the safest or most common action. For long or destructive content, focusing the heading or a neutral action may be better so the user can understand the message before acting. The exact target is a product decision, but it must be predictable and inside the dialog.

Always provide a visible close or cancel control. Escape support alone is not discoverable enough.

10. Hiding content correctly

Different techniques have different meanings:

Technique Visible In accessibility tree Takes layout space
hidden or display: none No No No
visibility: hidden No No Yes
Visually-hidden CSS No Yes Effectively no
aria-hidden="true" Usually yes No Yes

Never put aria-hidden="true" on a focusable element or an ancestor of one. It can leave something reachable by keyboard but absent from the accessibility tree.

11. Manual accessibility review

Manual checks find behavior and comprehension problems that a scanner cannot:

  1. Zoom to 200% and confirm content reflows without loss.
  2. Navigate the whole page with keyboard only.
  3. Confirm focus is always visible and follows a logical order.
  4. Operate every control without hover or precise pointer movement.
  5. Submit the form empty and follow the error-recovery path.
  6. Open the dialog, cycle focus, close with Escape, and check focus return.
  7. Inspect headings, landmarks, labels, names, roles, and states in browser tools.
  8. Use a screen reader for the critical flow and listen for labels, errors, and status updates.
  9. Check that meaning does not depend only on color, position, shape, or sound.

12. Automated checks are a safety net

Run browser accessibility inspection, axe, Lighthouse, or an equivalent rule engine early and in continuous integration when practical. These tools are excellent at detecting certain missing names, invalid ARIA, contrast failures, and structural errors.

Passing an automated scan does not prove the experience is accessible. A tool cannot reliably decide whether the heading describes the page, the focus order matches the task, the error is understandable, or a modal opens at the right moment. Combine automation with keyboard testing, zoom, screen-reader review, and human judgment.

13. Inspect the finished example

The prepared form demonstrates the full sequence:

  • Empty submission reveals a linked error summary.
  • Invalid fields receive aria-invalid and connected messages.
  • Focus moves to the summary so the failure is not silent.
  • Valid input opens a native review dialog.
  • The dialog has a visible title, cancel and confirm actions, Escape behavior, and focus return.
  • Confirmation is reported through a polite status region.
  • The interface remains operable at narrow widths and enlarged text.

No data is sent anywhere. The example exists only to expose the frontend behavior for inspection.

Common mistakes and fixes

Mistake Result Better approach
Clickable div used as a button Missing native keyboard and semantics Use <button>
Outline removed globally Keyboard location becomes invisible Style :focus-visible clearly
Placeholder used as label Context disappears during typing Keep a connected visible label
Error shown only in red Meaning depends on color Add specific text and programmatic association
Focus stays on submit after errors appear New information can be missed Focus the error summary or first invalid field
aria-live added everywhere Repetitive, disruptive announcements Announce only meaningful dynamic changes
Custom modal without complete behavior Focus escapes or cannot return Prefer native <dialog> or implement the full pattern
Automated score treated as proof Usability failures remain Combine tools with manual assistive-technology testing

Interview question and model answer

Question: How should focus behave when a modal opens and closes?

Model answer:

The modal is opened by a real interactive control. When it opens, focus moves to an appropriate element inside it, chosen according to the task and risk. While the modal is active, keyboard focus must remain inside the dialog and the background must be inert. The user can close it through a visible control and normally with Escape. After it closes, focus returns to the element that opened it unless that element no longer exists, in which case it moves to a logical nearby target. I prefer the native dialog element with showModal() because the browser supplies much of this behavior, but I still test initial focus, tab containment, Escape, accessible naming, and focus return with a keyboard and screen reader.

Quick recall sheet

  • Native controls provide semantics and keyboard behavior.
  • DOM order should match reading and focus order.
  • Never remove focus visibility without a strong replacement.
  • Labels name fields; descriptions provide extra guidance.
  • Errors need specific text, association, and a discoverable focus strategy.
  • Live regions announce meaningful dynamic changes without moving focus.
  • A modal moves focus inside, contains it, offers a close action, and returns focus.
  • Prefer native <dialog> for ordinary modal behavior.
  • Automated checks catch rules, not the entire user experience.
  • Test keyboard, zoom, errors, focus, and a critical screen-reader flow.
